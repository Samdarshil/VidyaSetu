# API Reference

Base URL: wherever you deploy `vidyasetu-backend` (e.g.
`https://your-service.onrender.com`). Interactive docs are also
auto-generated by FastAPI at `/docs` on that same URL once it's running.

All routes except `/auth/register` and `/auth/login` require a header:
```
Authorization: Bearer <token from login/register>
```

Role requirements are enforced server-side (`app/deps.py:require_role`) —
calling an endpoint with the wrong role's token returns `403`, not a
frontend-hidden button.

---

## Auth (`/auth`)

### `POST /auth/register`
- **Auth required:** no
- **Body:** `{ email, password, full_name, role, institution_name?, company_name? }` — `role` is one of `student | faculty | institution | industry | admin`.
- **Response:** `{ access_token, token_type, role, user_id, full_name }`
- **Notes:** creates the matching profile row (StudentProfile / FacultyProfile / Institution / Company) alongside the User in the same transaction.

### `POST /auth/login`
- **Auth required:** no
- **Body:** `{ email, password }`
- **Response:** same shape as register.

### `GET /auth/me`
- **Auth required:** yes (any role)
- **Response:** `{ id, email, full_name, role }`

## Student skills & evidence (`/students`)

### `GET /students/me/skills`
- **Auth:** student
- **Response:** list of `{ skill_name, self_declared_level, competency_score, evidence_confidence, last_verified_at, industry_demand_score, evidence: [...] }`

### `POST /students/me/skills/evidence`
- **Auth:** student
- **Body:** `{ skill_name, evidence_type, score_contribution, source_note? }` — `evidence_type` must be one of the values in `app/models/models.py:EvidenceType`.
- **Response:** the updated `StudentSkillOut`, recomputed from all evidence.
- **Notes:** creates the `Skill` and `StudentSkill` rows if they don't exist yet, then calls `recompute_student_skill()`.

### `POST /students/me/github-import`
- **Auth:** student
- **Body:** `{ github_username, repos: [{ name, primary_language?, description? }] }` — the `repos` array is expected to come from a client-side call to GitHub's own public API (`https://api.github.com/users/<username>/repos`), not from this backend.
- **Response:** `{ github_username, repos_processed, skills_updated: [...] }`
- **Notes:** only repos whose language maps to a skill VidyaSetu already tracks get evidence recorded (see `LANGUAGE_TO_SKILL` in `app/routers/skills.py`). No GitHub token is ever sent to or stored by this endpoint.

### `GET /students/me/gap-analysis`
- **Auth:** student
- **Response:** `{ target_role, readiness_percent, skills: [...], roadmap: [...] }`
- **Notes:** 400 if the student hasn't set a target role yet.

### `PATCH /students/me/target-role?role_title=<title>`
- **Auth:** student
- **Response:** `{ target_role }`

### `POST /students/me/simulate-skill`
- **Auth:** student
- **Body:** `{ skill_name }`
- **Response:** `{ skill_name, opportunities_before, opportunities_after, readiness_before, readiness_after, estimated_effort_hours, industry_demand }`
- **Notes:** simulates the named skill reaching competency 85, then recounts how many currently-active opportunities the student would qualify for (match ≥ 60%) — a real recount against live `Opportunity` rows, not a canned number.

## Assessments (`/assessments`)

### `GET /assessments`
- **Auth:** student
- **Response:** list of `{ id, title, skill_name, assessment_type, question_count }`

### `GET /assessments/{assessment_id}`
- **Auth:** student
- **Response:** `{ id, title, skill_name, questions: [{ id, text, options }] }`
- **Notes:** `correct_index` is stripped server-side before this response is built — the answer key never reaches the client.

### `POST /assessments/{assessment_id}/submit`
- **Auth:** student
- **Body:** `{ answers: { "<question_id>": <selected_option_index>, ... } }`
- **Response:** `{ score, correct_count, total_count, skill_name, updated_competency_score, updated_evidence_confidence }`
- **Notes:** scores server-side, persists an `AssessmentResult`, records a `SkillEvidence` row, and calls `recompute_student_skill()` — the result is real backend state, not a frontend-only number.

## Opportunities (`/opportunities`)

### `GET /opportunities`
- **Auth:** any role
- **Response:** list of `{ id, title, company_name, opportunity_type, location, work_mode, compensation, match_percent, matched_skills, missing_skills }`, sorted by match descending.
- **Notes:** `match_percent` is only meaningful for a student caller (computed against their real skills); other roles get `0` / full requirement lists since match is a per-student concept.

### `POST /opportunities`
- **Auth:** industry
- **Body:** `{ title, opportunity_type, location?, work_mode?, compensation?, description?, skill_requirements: [{ skill_name, required_level, weight }] }`
- **Response:** `{ id, title }`

### `POST /opportunities/apply`
- **Auth:** student
- **Body:** `{ opportunity_id }`
- **Response:** `ApplicationOut` including `match_score_at_apply`, computed and stored at the moment of applying.
- **Notes:** 400 if already applied to this opportunity.

## Applications (`/applications`)

### `GET /applications/me`
- **Auth:** student — the caller's own applications.

### `GET /applications/for-opportunity/{opportunity_id}`
- **Auth:** industry — 403 if the opportunity doesn't belong to the caller's own company.

### `PATCH /applications/{application_id}/status?new_status=<status>`
- **Auth:** industry (own company's opportunities only)
- **Notes:** valid `new_status` values are in `app/models/models.py:ApplicationStatus`. Creates a `Notification` for the student.

---

## Industry (`/industry`)

### `GET /industry/candidates?opportunity_id=<id>&min_match=<0-100>`
- **Auth:** industry (own opportunities only)
- **Response:** list of `{ student_id, name, institution_name, target_role, match_percent, matched_skills, missing_skills, avg_evidence_confidence }`, ranked by match.

### `GET /industry/skill-radar`
- **Auth:** industry, institution, or admin
- **Response:** list of `{ skill_name, industry_demand, academic_supply, gap_status }` — one real aggregate computation shared by both the Industry Skill Radar and Institution Skill Intelligence views.

---

## Institutions (`/institutions`)

### `GET /institutions/me/analytics`
- **Auth:** institution or admin
- **Response:** `{ institution_name, student_count, avg_readiness, heatmap: [...], critical_gaps: [...] }`

### `POST /institutions/me/intervention-simulator`
- **Auth:** institution or admin
- **Body:** `{ skill_name, duration_hours }`
- **Response:** `{ skill_name, students_ready_before, students_ready_projected, opportunities_unlocked_estimate, readiness_improvement_percent }`
- **Notes:** the training-program effect is modeled as a documented, tunable uplift (`min(45, duration_hours * 0.9)` added to each student's current competency) — an explainable formula, not a black box.

## Faculty (`/faculty`)

### `GET /faculty/me/profile`
- **Auth:** faculty

### `PATCH /faculty/me/profile`
- **Auth:** faculty
- **Query params:** `research_interests?`, `available_for_consultancy?`

### `GET /faculty/students`
- **Auth:** faculty
- **Response:** students in the faculty member's own institution only.

### `GET /faculty/students/{student_id}/skills`
- **Auth:** faculty
- **Response:** that student's real skills — 403 if the student belongs to a different institution than the caller.

### `GET /faculty/me/collaboration-matches`
- **Auth:** faculty
- **Response:** open collaboration requests whose text matches the faculty member's stated research interests.

## AI — "Ask Vidya" (`/ai`)

### `POST /ai/ask`
- **Auth:** any role
- **Body:** `{ question }`
- **Response:** `{ answer, reasons: [...], source }`
- **Notes:** rule-based and grounded only in the caller's own real platform data (see `app/engine.py:ai_explain_answer`) — it does not call an external LLM and cannot invent a skill, score, or opportunity that isn't in the database. `source` is always `"VidyaSetu Platform Data"` so the response's grounding is never ambiguous.
